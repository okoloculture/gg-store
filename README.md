# GG Store — магазин цифровых товаров

Витрина по макету + бэкенд с однократной выдачей ключей под гонками, восстановлением
после сбоев и промокодами с лимитом.

Стек: **Node.js** (`node:http`, без фреймворка), фронтенд — **чистые HTML/CSS/JS-модули**
без сборки. Хранилище — SQLite локально (`node:sqlite`) и PostgreSQL на деплое; движок
выбирается переменной окружения, код запросов общий. Единственная зависимость — `pg`,
и она подключается динамически: в режиме SQLite не загружается вообще, поэтому локальный
запуск и тесты по-прежнему работают без единой установки.

---

## Запуск

Нужен Node.js **22.5+** (используется встроенный `node:sqlite`). Проверено на Node 24.

```bash
git clone https://github.com/okoloculture/gg-store && cd gg-store
npm run reset     # создаёт БД, заливает каталог, пул ключей и промокоды
npm start         # http://127.0.0.1:3210
```

`npm install` нужен только для деплоя на Postgres: локально ни одна зависимость
не загружается.

| Страница | Адрес |
| --- | --- |
| Витрина | http://127.0.0.1:3210/ |
| Статус заказа | http://127.0.0.1:3210/order.html?id=ord_... |
| Админка | http://127.0.0.1:3210/admin.html (токен `dev-admin-token`) |

Настройки — переменные окружения, см. `.env.example` (порт, токен админки, движок БД,
доли сбоев поставщиков, таймауты).

### На PostgreSQL

```bash
createdb gg_store_dev
DATABASE_URL='postgresql://localhost:5432/gg_store_dev?sslmode=disable' npm run reset
DATABASE_URL='postgresql://localhost:5432/gg_store_dev?sslmode=disable' npm start
```

Схема, запросы и гарантии одни и те же: `?`-плейсхолдеры и `INSERT OR IGNORE`
переводятся в диалект Postgres в драйвере, различий в сервисах нет. Весь набор
сценариев ниже проходит на обоих движках.

## Проверка гонок

Сервер должен быть запущен в отдельном терминале. Рекомендуется чистая база
(`npm run reset`), чтобы числа в отчётах читались однозначно.

```bash
npm run acceptance        # ровно пять критериев приёмки из задания, 52 проверки
npm run race:all          # критерии приёмки + все состязательные сценарии + сводка
```

Отдельно:

```bash
npm run race:webhooks     # 50 параллельных вебхуков по одному заказу + повтор event_id
npm run race:buy          # 10 одновременных кликов "Купить" и 10 одновременных оплат
npm run race:out-of-order  # вебхук раньше заказа; failed->paid; поздний failed
npm run race:timeout      # ловушка таймаута поставщика + шторм из 15 заказов при сбоях
npm run race:stock        # пустой пул -> восстановление -> идемпотентная повторная выдача
npm run race:promo        # 40 параллельных применений промокода с лимитом 3
npm run race:restart      # SIGKILL посреди выдачи и восстановление после перезапуска
npm test                  # 15 юнит-тестов на отдельной БД (data/test.db)
npm run test:pg           # те же тесты на PostgreSQL (createdb gg_store_test, см. .env.test.pg)
```

Параметры: `PARALLEL=200 npm run acceptance`, `CLICKS=50 npm run race:buy`,
`STORM=40 npm run race:timeout`. Сценарий `race:restart` поднимает и убивает
собственный сервер на порту 3299 и отдельной БД, запущенный сервер ему не нужен
(на Postgres — база с суффиксом `_restart`, `createdb gg_store_restart`).

### Что именно проверяет `npm run acceptance`

| Критерий из задания | Как проверяется |
| --- | --- |
| 1. 50 параллельных вебхуков по одному заказу | 50 вебхуков с **разными** `event_id` разом; в БД ровно одна строка `deliveries`, ровно один ключ с `request_id`, ровно один `provider_issues` |
| 2. Повтор с тем же `event_id` | 5 повторов подряд; журнал событий не вырос, код, статус и число выдач не изменились |
| 3. Вебхук раньше заказа / не по порядку | вебхук по ещё не созданному заказу; `failed` → `paid`; поздний `failed` после `delivered` |
| 4. Пустой пул | пул осушается, оплата проходит, заказ в `out_of_stock`, сервер жив, ключ не списан; после пополнения повторная выдача даёт ровно один ключ, 5 повторов идемпотентны |
| 5. Промокод с лимитом N | 40 параллельных заказов с `LIMIT3`; принято ровно столько, сколько было свободных слотов, `used_count <= max_uses`, скидка посчитана сервером |

Плюс враждебные варианты, которых нет в списке критериев: 20 параллельных заказов
не делят один ключ; `failed` не приводит к выдаче; вебхуки по несуществующим заказам;
параллельные заказы с одним `Idempotency-Key` и промокодом; битые вебхуки → `400`.
В конце — сверка инвариантов по всей базе.

Каждый скрипт печатает список проверок и завершается ненулевым кодом при провале.
Инварианты проверяются не по ответам API, а по состоянию БД через `/api/admin/audit`:
один код в двух заказах, заказ с двумя списанными ключами, «осиротевший» ключ.

## Как обеспечена однократная выдача

Коротко: **все решения принимаются условным `UPDATE`/`INSERT` под `BEGIN IMMEDIATE`,
а не связкой «прочитали — подумали — записали»**, и на каждом шаге стоит уникальный
индекс, который физически не даёт продублировать факт.

Четыре независимых барьера, каждый достаточен сам по себе:

1. **Приём вебхука** — `payment_events.event_id PRIMARY KEY`. Повторная доставка того же
   события не проходит `INSERT OR IGNORE` и не меняет ничего. Статус заказа считается
   *свёрткой всего журнала событий*, а не отдельного события, поэтому порядок прихода
   вебхуков не важен, а успешная оплата не может быть перекрыта поздним `failed`.
2. **Аренда на выдачу** — переход в `delivering` возможен только одним условным `UPDATE`
   (`WHERE status IN (...) OR аренда протухла`). Из 50 параллельных попыток ровно одна
   получает `changes = 1`, остальные выходят, не тронув пул. `lease_token` отличает
   свою аренду от аренды воркера, перехватившего зависший заказ.
3. **Идемпотентность поставщика** — `request_id` детерминирован: `req_<order_id>_<provider>`.
   Любой повтор (после таймаута, рестарта, ручной повторной выдачи) попадает в тот же
   `request_id`, поставщик возвращает тот же код из журнала. `provider_keys.request_id UNIQUE`
   не даёт привязать один код к двум запросам.
4. **Факт выдачи** — `deliveries.order_id PRIMARY KEY` и `deliveries.code UNIQUE`. Даже если
   два воркера каким-то образом дошли до записи, строка появится одна; второй получит
   `changes = 0` и вернёт уже существующий код.

Двойной клик «Купить» гасится пятым барьером: `orders.idempotency_key UNIQUE` — повторный
запрос с тем же ключом возвращает уже созданный заказ, а не создаёт второй.

### Отдельно про таймаут поставщика

Таймаут и 5xx **не равны отказу**: код мог быть уже списан, а ответ потерян. Поэтому:

* повтор идёт к **тому же** поставщику и с **тем же** `request_id`;
* переключиться на резервного поставщика можно **только после явного `out_of_stock`** —
  по контракту поставщик, который уже выдал код под этим `request_id`, обязан вернуть
  тот же код, а не `out_of_stock`, значит `out_of_stock` доказывает, что он ничего не списал;
* после неоднозначного сбоя поставщик «залипает» (`orders.pending_provider`): все следующие
  попытки идут только к нему, пока он не ответит определённо.

Без этого правила шторм из 15 заказов при нестабильных поставщиках стабильно давал
заказы с двумя израсходованными ключами — сценарий `race:timeout` это ловит.

## Что реализовано

### Этап 1. Витрина и базовый флоу

Свёрстаны шапка, баннер-карусель, ряд иконок сервисов, блок пополнения Steam и ряд
карточек товара. Отзывы и футер не верстались (по заданию). Разметка сделана по
макету: цвета, размеры, отступы и тексты вынуты прямо из `.fig`-файла.

Флоу: «Купить» → `POST /api/orders` → модалка с кнопками эмуляции оплаты →
`POST /api/orders/:id/pay` шлёт вебхук по контракту на собственный эндпоинт →
автоматическая выдача → страница статуса `order.html?id=...`.

Обязательный интерактив:

1. **Баннер-карусель** — автопрокрутка (пауза при наведении и на скрытой вкладке),
   стрелки, активные точки-индикаторы.
2. **«Каталог»** — выпадающее меню, закрывается повторным кликом, кликом вне и Esc.
3. **Переключатель валют** `$ / ₸ / ₽` — меняет активное состояние и обозначение валюты
   у суммы и кнопки оплаты. Пересчёта суммы нет, как и указано в задании.
4. **Иконки сервисов** — плавный подъём, тень и подсветка рамки при наведении.
5. **Карточки товара** — подъём, усиление тени и обводка при наведении.

### Этап 2. Однократная выдача под гонками

См. раздел выше и `npm run race:webhooks`, `npm run race:buy`.

### Этап 3. Сбои и восстановление

Две заглушки поставщиков (A и B) за HTTP по контракту `POST /provider/:id/issue`.
Умеют отвечать 5xx, «зависать» с настраиваемым таймаутом и отдавать `out_of_stock`.
Доли сбоев настраиваются в рантайме через `POST /api/admin/providers/config`.

* Пул кончился → заказ переходит в `out_of_stock` (восстановимое состояние), сервер не падает.
* Оба поставщика недоступны → `delivery_failed`, фоновая сверка делает до 5 автоповторов.
* Админка показывает список «оплачен, но не выдан», умеет пополнять пул и запускать
  безопасную повторную выдачу. Повтор идемпотентен: тот же код, новый ключ не расходуется.
* Фоновая сверка (каждые 3 с) закрывает то, что не может закрыть один запрос:
  отложенные события, зависшие аренды, автоповторы.
* Процесс убит `SIGKILL` посреди выдачи → после перезапуска сверка видит протухшую
  аренду, повторяет запрос с тем же `request_id` и получает тот же код. Проверяется
  сценарием `npm run race:restart`.

### Этап 4. Промокоды

Лимит держится условным `UPDATE promocodes SET used_count = used_count + 1 WHERE
used_count < max_uses` в той же транзакции, что и создание заказа: при N параллельных
попытках ровно `max_uses` получают `changes = 1`. Скидку считает сервер от цены товара
из БД; любые суммы в теле запроса игнорируются. Если оплата не прошла — слот
возвращается, возврат идемпотентен.

## Статусы заказа

`created → paid → delivering → delivered` — основной путь.

| Статус | Смысл |
| --- | --- |
| `created` | создан, ждёт оплаты |
| `paid` | оплата подтверждена |
| `delivering` | идёт получение кода у поставщика (под арендой) |
| `delivered` | код выдан (финальный) |
| `payment_failed` | оплата не прошла (финальный) |
| `out_of_stock` | оплачено, кода нет — **восстановимо** |
| `delivery_failed` | поставщики не смогли выдать — **восстановимо** |

## API

### Публичное

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/api/catalog` | каталог товаров |
| `POST` | `/api/orders` | создать заказ; заголовок `Idempotency-Key`, тело `{sku, promo_code?, steam_login?, order_id?}` |
| `GET` | `/api/orders/:id` | статус заказа и выданный код |
| `POST` | `/api/orders/:id/pay` | эмуляция оплаты `{outcome: "success" \| "fail"}` — шлёт вебхук |
| `POST` | `/api/promo/preview` | серверный расчёт скидки `{code, sku}` |
| `POST` | `/api/webhooks/payment` | эндпоинт платёжной системы |

`order_id` в теле создания заказа нужен только для тестов: он позволяет отправить
вебхук раньше, чем заказ создан.

Вебхук по контракту:

```json
{ "event_id": "evt_a1b2c3", "order_id": "ord_00123", "status": "paid",
  "amount": 500, "currency": "RUB", "created_at": "2025-01-01T12:00:00Z" }
```

Отвечает быстрым `200`, выдача уходит в фон. Подпись не проверяется (по заданию).

### Админка (заголовок `x-admin-token`)

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/api/admin/orders?status=stuck` | «оплачен, но не выдан» |
| `POST` | `/api/admin/orders/:id/redeliver` | идемпотентная повторная выдача |
| `GET` | `/api/admin/stock` | остаток пула, настройки поставщиков, промокоды |
| `POST` | `/api/admin/keys/refill` | пополнить пул `{provider, sku, count \| codes}` |
| `POST` | `/api/admin/keys/drain` | осушить пул (для теста out_of_stock) |
| `POST` | `/api/admin/providers/config` | доли сбоев: `{A: {failRate, timeoutRate, timeoutMs, forced}}` |
| `POST` | `/api/admin/reconcile` | прогнать сверку немедленно |
| `GET` | `/api/admin/audit` | глобальные инварианты |
| `GET` | `/api/admin/audit/:id` | инварианты по заказу |

### Заглушки поставщиков

`POST /provider/a/issue`, `POST /provider/b/issue` — тело `{request_id, sku, order_id}`,
ответ `{status:"ok", request_id, code}` либо `{status:"error", reason}`.

## Деплой на Vercel

Витрина (`public/`) раздаётся как статика, весь бэкенд — одна serverless-функция
`api/index.js`, хранилище — управляемый PostgreSQL (Neon / Vercel Postgres).

```bash
npm i -g vercel && vercel login
vercel link
vercel env add DATABASE_URL production     # строка подключения к Postgres
vercel env add ADMIN_TOKEN production      # не оставлять dev-admin-token
vercel --prod
```

Каталог, пул ключей и промокоды заливаются один раз:

```bash
DATABASE_URL='<строка подключения>' npm run setup
```

Если база пуста, функция сделает это сама при первом холодном старте.

### Чем serverless отличается от локального запуска

Три вещи, которых на Vercel нет, и что стоит вместо них:

| Локально | На Vercel |
| --- | --- |
| диск под SQLite | управляемый PostgreSQL, `DATABASE_URL` |
| фоновая сверка каждые 3 с | Vercel Cron (`/api/cron/reconcile`) плюс точечная сверка при опросе статуса заказа |
| выдача уходит в фон после ответа на вебхук | вебхук дожидается выдачи: после ответа инстанс замораживается |

Точечная сверка нужна потому, что на тарифе Hobby планировщик срабатывает раз в
сутки: страница заказа опрашивает свой статус, и этот же запрос применяет
отложенные события и перезапускает застрявшую выдачу. Между автоповторами
выдерживается пауза `RECONCILE_INTERVAL_MS`, иначе частый опрос израсходовал бы
бюджет попыток за секунды, пока поставщик ещё лежит.

Брошенная на полпути попытка (инстанс заморожен после ответа) безопасна ровно по
той же причине, что и убитый `SIGKILL` процесс: код закреплён за детерминированным
`request_id`, аренда протухает, следующая попытка получает от поставщика тот же код.

Переменные окружения для продакшена: `DATABASE_URL`, `ADMIN_TOKEN`, `CRON_SECRET`,
`PUBLIC_BASE_URL` (адрес, по которому функция ходит в собственные заглушки
поставщиков), при необходимости — доли сбоев поставщиков.

## Что не делалось (по заданию)

Реальный эквайринг, проверка подписи вебхука, авторизация покупателя, отзывы, футер,
мобильная и тёмная версии, пиксель-перфект, дизайн страницы статуса и админки.

## Данные каталога

Товары, пул из 50 ключей и промокоды взяты из материалов задания (`src/db/catalog.json`).
50 ключей разложены по SKU типа `key` и по двум поставщикам
(`KEY-CS2-PRIME` 18/8, `KEY-GTA5` 8/4, `KEY-EFT` 8/4). Для остальных SKU пулы
сгенерированы детерминированно (6 у A, 3 у B) — маленькие намеренно, чтобы сценарий
`out_of_stock` воспроизводился без подготовки.
